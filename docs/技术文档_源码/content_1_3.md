                                                      │
                                              ┌───────┴───────┐
                                              │       │       │
                                            OLED    蓝牙    串口
                                           (盘子里) (外卖)  (后厨日志)

                    │  Get_StepCount│
                    └───────┬───────┘
                            │
              ┌─────────────┼─────────────┐

         vTaskDisplay  vTaskBT     vTaskVoice

**关键原则**：
- 传感器只负责读硬件，不关心数据怎么用（单一职责）
- 算法只负责计算，不关心数据从哪来（纯函数思想）
- 显示/蓝牙只负责输出，不关心数据怎么算的（解耦）

## 第2章 嵌入式通信协议入门

在深入代码之前，先理解单片机怎么跟传感器"说话"。这就像人类用不同语言交流——有的用有线电话（I2C），有的用对讲机（UART），有的用旗语（1-Wire）。

### 2.1 I2C —— 两根线的"快递系统"

**类比**：想象一个大楼里只有一个快递收发室，每个房间有唯一门牌号。快递员用两根线：一根是"同步时钟"（大家按同一节奏走），一根是"数据"（真正传输的信息）。

```
SCL (时钟)  ──┐ ┌──┐ ┌──┐ ┌──┐ ┌──   就像节拍器，滴滴滴...
             └─┘  └─┘  └─┘  └─┘
SDA (数据)  ──┬─┬──┬──┬──┬──┬──   每个时钟周期传一个 bit
             1 0  1  1  0  1  0
```

**I2C 的三个关键概念**：

**① 设备地址**：每个 I2C 设备出厂时有一个 7-bit 地址。写地址 = 地址左移1位。

```
MAX30102: 7-bit 地址 0x57 = 0101 0111
          8-bit 写地址 0xAE = 1010 1110  (0x57 << 1)
          ↑ 这就是代码里 MAX30102_I2C_ADDR 的意思
```

**② 读写流程**：每次通信都是一次"事务"：

```
主机发送: START → 设备地址(W) → 寄存器地址 → [数据...] → STOP
主机接收: START → 设备地址(W) → 寄存器地址 → START → 设备地址(R) → [数据...] → STOP
                                              ↑
                                         这个叫"重复起始"，告诉设备：我要读，不是写
```

**③ 上拉电阻**：I2C 的 SDA/SCL 必须各接一个 4.7kΩ 电阻到 3.3V。为什么？
设备只能把线"拉低"（输出 0），不能"推高"。上拉电阻在没人拉低时把线"抬起"到 3.3V。就像弹簧门——你只能推开门，松手后弹簧把门弹回来。

**本项目中的两条 I2C 总线**：

| 总线 | 引脚 | 挂载设备 | 为什么这样分？ |
|------|------|---------|--------------|
| I2C1 | PB6/PB7 | MAX30102 + MPU6050 | 两个传感器都需要高速连续读取 |
| I2C2 | PB10/PB11 | SSD1306 OLED | 屏幕独占一条总线，避免跟传感器争抢 |

### 2.2 UART —— "对讲机"通信

**类比**：两个人各拿一个对讲机。没有时钟线——双方约定好说话速度（波特率），各说各的。

```
PA9 (TX)  ────────────────→  HC-05 RX    发送
PA10 (RX) ←────────────────  HC-05 TX    接收

波特率 = 9600 = 每秒传 9600 个 bit
每字节 = 1 起始位(0) + 8 数据位 + 1 停止位(1) = 10 bit
实际每秒传 9600/10 = 960 字节 ≈ 1KB/s
```

**本项目用的两组串口**：

| 串口 | 引脚 | 用途 | 波特率 |
|------|------|------|--------|
| USART1 | PA9/PA10 | HC-05 蓝牙 + 调试输出 | 9600 (蓝牙) / 115200 (调试) |
| USART2 | PA2/PA3 | ASR PRO 语音识别 | 9600 |

**关键代码片段理解**（来自 `uart_hal.c`）：

```c
// 发送一个字节，等硬件说"发送完了"再发下一个
for (uint16_t i = 0; i < len; i++) {
    USART_SendData(usart, data[i]);              // 把数据丢给硬件
    while (USART_GetFlagStatus(usart, USART_FLAG_TXE) == RESET) {}
    //  ↑ 死等——直到硬件发送缓冲区空了才继续
}
```

### 2.3 1-Wire —— "单线旗语"

**类比**：两个人在望远镜可见的距离用旗语通信——只有一个信道，需要严格的时序。

DS18B20 只用一个引脚 PA0 完成双向通信。没有时钟线，靠精确的时间间隔来区分 0 和 1：

```
写 "1": 拉低5微秒 → 拉高65微秒    (短的拉低 = 逻辑1)
写 "0": 拉低65微秒 → 拉高5微秒    (长的拉低 = 逻辑0)

读一个 bit:
  拉低2微秒 → 拉高 → 等8微秒后读电平 → 等55微秒
  ↑ 这个"读窗口"非常窄，必须关中断防止被干扰
```

**这就是为什么 DS18B20 读写都用 `taskENTER_CRITICAL()` 包起来**——它关掉了任务切换，保证时序不被 FreeRTOS 打断。

**1-Wire 数据手册定义的命令序列**：

```
启动转换: Reset → 0xCC (Skip ROM) → 0x44 (Convert T)
         └─ 单设备模式，跳过64-bit ROM码 ─┘ └─ 开始温度转换，750ms ─┘

读取结果: Reset → 0xCC (Skip ROM) → 0xBE (Read Scratchpad)
         └─ 读9字节，最后1字节是CRC校验 ─┘
```

## 第3章 FreeRTOS 是怎么让单片机"同时做多件事"的

### 3.1 为什么需要操作系统？

**类比：没有 FreeRTOS vs 有 FreeRTOS**

没有操作系统时，你的代码像一个单线程的厨子：

```c
int main() {
    while(1) {
        读MAX30102();    // 花了50ms
        读MPU6050();     // 花了30ms
        刷新OLED();      // 花了100ms
        处理蓝牙();       // 花了80ms
        // 总共260ms一轮，期间如果有蓝牙数据来了，只能等下次循环
    }
}
```

有了 FreeRTOS，变成了一个有四个厨子的厨房，每个厨子负责一件事：

```
时间轴 ────────────────────────────────────────────────────→
vTaskSensors   ██░░░░░░░░██░░░░░░░░██░░░░░░░░    每200ms工作一次
vTaskDisplay   ░██░░██░░██░░██░░██░░██░░██░░    每50ms工作一次
vTaskBT        ░░█░█░█░█░█░█░█░█░█░█░█░█░█    每20ms工作一次
vTaskVoice     ░░░███░░░░███░░░░███░░░░███░░    每100ms工作一次
```

因为有 4 个任务轮流运行，蓝牙数据一来就能及时处理，不会因为屏幕刷新而卡住。

### 3.2 任务是怎么切换的？

CPU 只有一个。FreeRTOS 用"时间片轮转 + 优先级抢占"来制造"同时运行"的假象：

```
规则1（抢占）：优先级高的任务就绪时，立即抢走CPU
规则2（轮转）：同优先级的任务轮流跑，每人跑1个tick（本项目1ms）
规则3（阻塞）：任务调用 vTaskDelay() 后主动放弃CPU，等待期间不占资源
```

**本项目任务优先级**：

```
优先级3: vTaskSensors    ← 最高！传感器数据不能丢
优先级2: vTaskDisplay    ← 中间
优先级2: vTaskVoice      ← 中间
优先级2: vTaskBluetooth  ← 中间
优先级1: IDLE任务         ← 最低，没人干活时跑
```

Sensors 优先级最高——MAX30102 的 FIFO 只有 32 个样本位，100Hz 采样率意味着 320ms 就会溢出。如果 Sensors 任务被阻塞超过 320ms，数据就丢了。

### 3.3 vTaskDelay 是怎么工作的？

```c
vTaskDelay(pdMS_TO_TICKS(200));  // "我要睡200毫秒，让其他人干活"
```

这个函数调用后发生了什么：

1. FreeRTOS 把当前任务标为"阻塞"
2. 从就绪列表中找一个任务开始跑
3. 200ms 后，FreeRTOS 把当前任务标回"就绪"
4. 如果没人占着 CPU，当前任务继续跑

**为什么不用 `Delay_ms(200)` ？**

```c
Delay_ms(200);   // 忙等——CPU 空转 200ms，什么事都不干
vTaskDelay(pdMS_TO_TICKS(200));  // 阻塞——CPU 这 200ms 去干别的事
```

区别就像你在银行排队：
- `Delay_ms` = 你站在窗口前发呆 200 秒，后面的人干等着
- `vTaskDelay` = 你拿个号坐着等，叫到你才过去，其他人继续办业务

### 3.4 互斥锁（Mutex）——"厕所锁"

MAX30102 和 MPU6050 共享 I2C1 总线。如果两个任务同时操作同一条总线，信号会乱掉。

```c
// 任务A: 读 MAX30102
xSemaphoreTake(g_i2c_mutex, 100ms);  // "锁门"
I2C_WriteReg(...);                   // 安全操作
xSemaphoreGive(g_i2c_mutex);         // "开门"

// 任务B: 读 MPU6050
xSemaphoreTake(g_i2c_mutex, 100ms);  // 等门开——最多等100ms
I2C_WriteReg(...);
xSemaphoreGive(g_i2c_mutex);
```

**为什么不用全局变量 `busy = 1` 来锁？**
因为 FreeRTOS 可能在任意时刻切换任务。如果任务 A 刚设 `busy = 1` 还没开始用总线，就被任务 B 抢走了 CPU，任务 B 看到 `busy = 0`（因为 A 还没来得及设）然后也去用总线——这就是"竞态条件"。Mutex 是硬件级别的原子操作，不会出现这个问题。

### 3.5 临界区（Critical Section）——"请勿打扰"

```c
taskENTER_CRITICAL();   // 关中断，关任务切换
ow_write_byte(0xCC);    // 1-Wire 时序不能被中断打断！
ow_write_byte(0x44);
taskEXIT_CRITICAL();    // 恢复正常
```

临界区比 Mutex 更强——它直接关掉了任务切换和部分中断。但用多了系统会变"卡"，所以只在必须的地方用（1-Wire 时序、步数累加等微秒级操作）。
